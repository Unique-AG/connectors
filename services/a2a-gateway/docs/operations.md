# Operations

## Lifecycle of gateway data

The gateway stores protocol state only. Chats, messages, files and elicitations stay in core and are never deleted by the gateway.

| Data | Kept until | Purged by |
| --- | --- | --- |
| Inbound tasks (with artifacts and push configs) | `TASK_RETENTION_DAYS` after their last status change, terminal tasks only | maintenance `lifecycle.retention` |
| Inbound contexts (A2A `contextId` → chat) | no task left and idle for `TASK_RETENTION_DAYS` | maintenance |
| Outbound executions (usage attribution) | `EXECUTION_RETENTION_DAYS`, terminal executions only | maintenance |
| Chat → remote context mappings | no execution left and idle for `TASK_RETENTION_DAYS` | maintenance |
| Connections no space uses (failed create, replaced) | 24 h and no execution history | maintenance |
| Revoked credentials | removed immediately on revoke; the connection configuration is kept | `DELETE /management/connections/:id/credentials` |
| Publications of deleted spaces | disabled on deletion (core hook) and by reconciliation | maintenance `lifecycle.reconcile-publications` |

Maintenance runs every `RECONCILE_INTERVAL` seconds as one absurd task per interval boundary, so any number of replicas schedule it exactly once. Each purge is bounded per tick. Access is always re-authorized against core, so a missed purge or reconciliation never grants access.

## Recovery

- **Outbound**: an execution records its absurd task. A run whose task ended without settling it (retries exhausted, lost worker) is restarted from the recorded remote task, up to 3 times, then reported in the chat as unknown. A turn is never re-sent: a crash after `sending` is reported as unknown.
- **Inbound**: executors heartbeat running tasks. Tasks without a heartbeat for 90 s are adopted by a durable watcher that follows the native turn in core and updates the snapshot; subscribers on any replica follow that snapshot. A crash between creating the native message and recording it fails the task as unknown instead of running it twice.
- **Rolling restarts** are safe: absurd reclaims leases of stopped workers and the recovery above applies. Stop replicas with `SIGTERM`; the worker and pool close through Nest shutdown hooks.

## Signals and alerts

Prometheus metrics (`OTEL_METRICS_EXPORTER=prometheus`):

| Metric | Use |
| --- | --- |
| `a2a_gateway_active_runs{company_id,direction}` | load |
| `a2a_gateway_stuck_runs{company_id,direction}` | alert when > 0 for 30 min |
| `a2a_gateway_runs_finished_total{company_id,direction,state}` | failure rate (`state=failed|unknown`) |
| `a2a_gateway_run_duration_seconds` | latency |
| `a2a_gateway_quota_rejections_total` | quota pressure |
| `a2a_gateway_bytes_total` | traffic |

Logs: `alert: "a2a-stuck-runs"` for stuck runs, `action: "push.failed"` for webhook failures, and `audit: true` records for configuration, invocation, cancellation, quota and file access. Logs contain ids and states only.

`GET /management/usage?from&to` returns per-space, per-connection and per-client usage (runs, users, duration, bytes) for Space Managers of the company.

## Disabling and uninstalling

| Action | Running work | New work | Retained data |
| --- | --- | --- | --- |
| Rollout flag `FEATURE_FLAG_ENABLE_A2A` off | continues with ongoing authorization; read, cancel, revoke allowed | rejected (publish, configure, invoke) | everything |
| Publication disabled or space deleted | inbound tasks finish and stay readable/cancelable | new sends rejected, card 404 | tasks until retention |
| Connection credential revoked | the next remote call fails; the chat shows a connection error | rejected until a new credential is tested | configuration, executions |
| External space deleted | outbound runs fail on their next authorization check | — | executions until retention; the connection is unbound and purged |
| Gateway scaled to 0 / outage | resumes on restart (see Recovery) | core reports A2A as temporarily unavailable, configuration is kept | everything |
| Gateway uninstalled (`A2A_GATEWAY_URL` unset) | stops; remote agents may still finish their tasks | core hides A2A, native spaces unaffected | the gateway database until you drop it |

Remote agents are not notified of an uninstall. Cancel running outbound work first if remote side effects matter.

## Backup, restore and migrations

- The gateway database holds gateway tables and the absurd schema; back it up with the platform's PostgreSQL backups. There is no other state.
- Credentials are encrypted with `ENCRYPTION_KEY`. Back up the key with the database; without it connections must be re-entered.
- After a restore, running executions are recovered or reported as unknown; tasks older than the backup are unknown to clients.
- Migrations are generated by drizzle-kit and applied before the service starts (`pnpm db:migrate`). They only add columns or constraints compatibly with the previous release, so replicas can roll.
