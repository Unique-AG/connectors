## Fallback without client elicitation support

Each server picks its own policy; there is no shared helper.

- **aws-api-mcp-server: fail closed, by error code, not capability.** `check_elicitation_support` is just `hasattr(ctx, 'elicit')` ([policy.py#L32-L39](https://github.com/awslabs/mcp/blob/2ed7f904ae146f5d8bc8e775cbdf69d95e8484ef/src/aws-api-mcp-server/awslabs/aws_api_mcp_server/core/security/policy.py#L32-L39)), which is always true for a FastMCP `Context`, so the "treat elicitList as deny" branch is effectively dead. In practice the prompt is sent and a `METHOD_NOT_FOUND` reply becomes "Client does not support elicitation. Use a different client or update the server configuration." Opt-out is configuration: leave `REQUIRE_MUTATION_CONSENT` false (the default) and keep commands off `elicitList`. DEPLOYMENT.md notes Bedrock AgentCore does not support elicitation.
- **aws-for-sap-management: fail closed, no opt-out.** Consent is unconditional for every mutating tool; `METHOD_NOT_FOUND` -> "Client does not support elicitation. Cannot proceed without user confirmation for this operation." Other MCP errors are re-raised (also a failed call).
- **aws-transform-mcp-server: degrade to re-call.** Checks `session.check_client_capability(ClientCapabilities(elicitation=...))`; if absent or the elicitation throws, returns a structured `isError` result `PROFILE_SELECTION_REQUIRED` / `REGION_SELECTION_REQUIRED` with the list of choices and `suggestedAction` "Re-call configure with profileName set to one of the names below" / "Ask the user which region they want, then call switch_profile with the region parameter." The tool argument is the fallback channel.
- **redshift-mcp-server: fail closed with a named opt-out.** Checks the capability explicitly before returning `Elicit`, raising `ToolError` "This MCP client cannot prompt for confirmation, so the statement was not run. Use a client that supports elicitation, or set UNSAFE_SKIP_WRITE_CONFIRMATION=true to execute writes unconfirmed." ([server.py#L299-L307](https://github.com/awslabs/mcp/blob/2ed7f904ae146f5d8bc8e775cbdf69d95e8484ef/src/redshift-mcp-server/awslabs/redshift_mcp_server/server.py#L299-L307)). No prompt at all in the default `read-only` access mode.

## Other human-in-the-loop mechanisms

- Env/CLI gating is the dominant pattern across the monorepo: 17 servers reference an `--allow-write` / `allow_write` flag and 5 an `--allow-sensitive-data-access` flag; aws-api-mcp-server has `READ_OPERATIONS_ONLY`; redshift has `ACCESS_MODE=read-only|read-write`.
- aws-api-mcp-server: user-maintained `denyList` / `elicitList` policy file (exact-match CLI strings) layered over IAM.
- redshift: annotations switch with access mode (`readOnlyHint`/`destructiveHint` true in read-write), plus a SQL guard that rejects non-executable statements before any prompt.

## Notes

- Only 4 of 62 servers use elicitation; all others rely on startup flags and IAM.
- redshift-mcp-server is the only Python example here written against the SDK v2 `Elicit`/`Resolve` abstraction, which lets one tool body work under both the legacy request and the 2026-07-28 multi-round-trip shape. Their comment notes the resolver runs twice under MRTR (once to ask, once on the retry), so it must be side-effect free and its log lines bracket the user's think time.
- redshift deliberately prompts even for writes the server is about to refuse, to avoid a race between the check and the tool body.
- aws-api-mcp-server's capability check is a no-op (`hasattr`), worth citing as a pitfall.
- The SAP HANA stop prompt is the one case where a confirmation form also collects a real decision (cascade-stop dependent apps).
