# MCP architecture

Every Python MCP in this repo is generated by `packages/mcp-scaffold` and keeps the shape this
file describes. It is the contract for writing code inside one. Most of it is enforced by ruff,
basedpyright, import-linter and `poe architecture`: a change that breaks a rule fails one
of them, and the failure names the import or the line at fault and how to fix it.
`bash ../../scripts/check-python-service.sh .` runs them all, in the order CI does.

`<package>` below is the MCP's Python package, `weather_mcp` for `services/weather-mcp`.
Example paths such as `contexts/prices/get_latest_close.py` come from
`services/architecture-demo-mcp`.

## What the MCP owns and what it shares

Every file the scaffold wrote is the MCP's own: change it as the MCP needs, nothing regenerates
it. What every MCP shares comes from a package it depends on, so a fix reaches every MCP with a
version bump:

- `packages/mcp-configs`: the settings with their defaults. Fix a shared setting there, never
  only in one service.
- `packages/mcp-observability`: the logs, traces and metrics, and the `/probe`, `/health` and
  `/metrics` routes, which `telemetry/setup.py` sets up.
- `packages/mcp-openapi`: the retry policy of every upstream client, and for an OpenAPI
  upstream the client and the codegen.
- `packages/mcp-architecture`: this file, the code style and type check the MCP extends, the
  import contracts and the architecture check.

A change to `packages/mcp-scaffold` only reaches the MCPs it makes next.

A file the scaffold wrote starts with a comment such as
`# mcp-scaffold-commit: 3f2a9c1e5b7d, timestamp: 2026-10-21T09:30:00+00:00`, the commit the
scaffold ran from. Leave it on a file you
edit, and drop it from a scaffold file you rewrite from scratch. Never add one to a file you
write, even one modelled on a stamped file, nor to a file a tool writes, such as `uv.lock`, the
codegen's output, an Alembic migration or the tool surface snapshot.

## Use what exists before writing code

1. FastMCP. Read the installed package in `.venv/lib/python3.14/site-packages/fastmcp/`: its
   server and tool middleware, `Depends` and `CurrentContext`, elicitation, providers such as
   `FileSystemProvider` and `OpenAPIProvider`, auth and its exceptions.
2. The packages every MCP shares: `mcp-configs` for settings, `mcp-observability` for logs,
   traces and metrics, `mcp-openapi` for an upstream's client, retries and locks, and
   `unique_mcp` for Zitadel sign-in.
3. A library the MCP already depends on, such as SQLAlchemy, `py-key-value-aio` or pydantic.

Write code only for what none of them provide.

## Layers

```
main.py ─▶ mcp ─▶ contexts ─▶ upstream ────┐
                          └─▶ persistence ─┴─▶ shared ─▶ telemetry
```

| Layer | Owns | May import |
|---|---|---|
| `main.py` | Starts telemetry, builds the server, runs it | everything |
| `mcp/` | The FastMCP server, its HTTP serving and middleware, auth, tools and their inputs and responses | `contexts`, `upstream`, `persistence`, `shared`, `telemetry` |
| `contexts/` | The domain: one folder per feature | `upstream`, `persistence`, `shared`, `telemetry` |
| `upstream/` | The system the MCP fronts: its client, settings and, for OpenAPI, the spec and generated code | `shared`, `telemetry` |
| `persistence/` | Storage the MCP owns: Postgres, Redis, a key-value store | `shared`, `telemetry` |
| `shared/` | What more than one layer uses: `contracts/`, the types two layers agree on without importing each other, and `utils/`, helpers such as a formatter. [`guides/shared.md`](guides/shared.md) says what belongs there | `telemetry` |
| `telemetry/` | Tracing, logging, metrics and the ops routes | nothing in the package |

`upstream` and `persistence` do not import each other. The package holds these and nothing else:
a new top-level folder or module, such as `<package>/logic/`, breaks the `layers` contract. An
unused `upstream`, `persistence` or `shared` stays as an `__init__.py` with an empty `__all__`.

## The rules

| Rule | Enforced by |
|---|---|
| A layer only imports the layers below it, and the package holds no module outside them. | import-linter `layers` contract |
| A layer is imported through its top level, `from <package>.upstream import X`, never `from <package>.upstream.client import X`. Inside a layer, deep imports are fine. | import-linter `protected` contracts |
| Outside `contexts/`, code imports the domain from `<package>.contexts` only: `from <package>.contexts import get_price_performance`, never `from <package>.contexts.prices import get_price_performance`. | import-linter `protected` contract on `contexts` |
| Inside `contexts/`, a feature imports another through that feature's top level: `from <package>.contexts.prices import get_latest_close`. Inside a feature, deep imports are fine. | import-linter `feature_privacy` contract, the one contract type of our own |
| No package imports its siblings in a cycle (`a → b → c → a`), at any depth: features in `contexts/`, folders in `mcp/`, modules inside a feature. | import-linter `acyclic_siblings` contract |
| `contexts/`, `persistence/` and `shared/` import nothing from `fastmcp`, `mcp` or `mcp_types` themselves. | import-linter `forbidden` contract |
| `shared/contracts/` holds types, not implementations: it imports nothing from `sqlalchemy`, `httpx2` or `cryptography`. | import-linter `forbidden` contract |
| Every folder with Python code has an `__init__.py`, since import-linter does not see the others. | ruff `INP001` |
| A function takes at most three positional arguments, and names the rest after a `*`: `def f(a, b, *, c, d)`. | ruff `PLR0917` |
| Imports are absolute. | ruff `TID252` |
| What a past fix replaced stays replaced: a pydantic model, not a `dataclass`; `httpx2.URL` or `HttpUrl`, not `urllib.parse`; `mcp_configs.PostgresSettings`, not `ssl.create_default_context`; a Jinja2 template, not `html.escape`; `cryptography.fernet`, not `cryptography.hazmat`. | ruff `TID251` |
| The [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html), as far as ruff checks it, with four departures: lines run to 100 characters, a docstring is only for what the code cannot say, its summary may run onto a second line, and a TODO names a link rather than an author. Besides it: no `print`, `pathlib` over `os.path`, no `else` after `return`, a long string split by implicit concatenation rather than `+`, and an error logged in an `except` with its traceback. | ruff, with `code_style.toml` |
| Every type is known: no `Any`, no unannotated attribute, `@override` on an override, `super().__init__()` in a subclass. A test may use a private name of the code it tests. | basedpyright `all`, with `type_check.json` |
| No file changes its own type check: a `# pyright:` comment only ignores a named rule on its line. | `uv run poe architecture` |
| No file turns a lint rule off beyond one line: no `# ruff: noqa` or `# ruff: disable` comment outside `upstream/generated/`. | `uv run poe architecture` |
| Every tool has a description and every parameter a `Field(description=...)`. | `uv run poe architecture` |
| Every tool's input schema is a plain object, with no `anyOf`, `oneOf`, `allOf` or `not` at its root, which some clients reject. | `uv run poe architecture` |
| An unexpected error inside a tool reaches the client without its message: `FastMCP(mask_error_details=True)`. | `uv run poe architecture` |
| A settings error does not print the value it was given, which may be a secret: every settings class builds its `model_config` with `mcp_configs.shared_config`. | `uv run poe architecture` |
| What every tool shows a client matches `tests/tool_surface.generated.json`. | `uv run poe architecture` |
| `contexts/` is flat: each folder in it is a feature named for its domain, and a feature never contains another. A tool folder does not nest. A context module leads with its one public function. | review |

Never loosen a rule to make a change pass. CI runs each tool with the MCP's own configuration, so
nothing stops an edit to `[tool.ruff]`, `[tool.basedpyright]` or `[tool.importlinter]` but review.
Treat that as yours to hold. When a check fails, try everything else first: move the code to where
it belongs, change its design, or narrow its types. Only when the line truly cannot comply, name
the rule in a `# noqa: <rule>` or `# pyright: ignore[<rule>]` on that one line, with the reason
beside it. Never turn a rule off in a table, for a file or for a folder, never drop or narrow a
contract, and never add an `ignore_imports` entry. If you believe a rule is wrong, stop and tell
the user rather than loosening it.

## The top level is the interface

Each layer's and each feature's `__init__.py` re-exports what others may use and lists it in
`__all__`. Anything not listed there is internal. When another layer needs something internal,
decide whether it belongs in the interface, and add it to `__init__.py` if it does.

`contexts/__init__.py` re-exports what the tools use from every feature, so `mcp/` imports
`from <package> import contexts` and calls `contexts.get_price_performance`, never naming a
feature. Its names are one flat list, so they are unique across features. A feature's own
`__init__.py` re-exports what other features may use, as `prices` does with `get_latest_close`.

`upstream` and `persistence` expose the same names in every MCP that has them, whatever is
behind them:

| `upstream` | `persistence` | |
|---|---|---|
| `Upstream` | `Persistence` | What the contexts receive |
| `UpstreamSettings` | `PersistenceSettings` | Its settings, read from the environment |
| `open_upstream(settings, transport)` | `open_persistence(settings)` | An async context manager the server lifespan opens. `transport` stands in for the upstream in tests. An OpenAPI upstream takes `open_upstream(http, settings)`, the client it shares with the tools served from the spec |
| `UpstreamError` | | A `ToolError`, so it passes through a context and reaches the client with the status, method and URL. [`guides/upstream.md`](guides/upstream.md) says where the error body goes |

An MCP scaffolded with `--auth credentials` exports a few more: `open_upstream` (and for OpenAPI
`upstream_http`) also takes the `CredentialsProvider` each request is signed with, `upstream`
exports `verify_credentials`, and `persistence` exports `SqlAuthStore` and `AuthStoreSettings`.
[`guides/auth.md`](guides/auth.md) lists what each layer holds.

`Upstream` is the client's own type: an alias of `OperationClient` for OpenAPI, and the class in
`upstream/client.py` for a custom upstream. It is not an abstraction: a context calls the
client's own API, so changing the client changes them too.

## Commands

`[tool.poe.tasks]` in the MCP's `pyproject.toml` names each command; `uv run poe` lists them.

```bash
# install
uv sync
# every check CI runs, in its order
uv run poe ci
# or one at a time
uv run poe fix            # ruff format and ruff check --fix
uv run poe typecheck
uv run poe imports
uv run poe architecture
uv run poe surface        # records what a client sees, when you meant the change
uv run poe test
uv run poe codegen        # an OpenAPI upstream: regenerate from the spec, --refresh-spec to fetch it
# serve on http://127.0.0.1:8000/mcp, after cp .env.example .env
uv run <name>
```
