# MCP architecture

Every Python MCP in this repo is generated by `packages/mcp-scaffold` and keeps the shape this
file describes. It is the contract for writing code inside one, and each MCP's `AGENTS.md`
points here before it says what that MCP chose. Most of it is enforced: a change that breaks a
rule fails `uv run pytest`, and the failure names the import or folder at fault. Type errors and
formatting are not: run `uv run basedpyright` and `uv run ruff format --check .` as well.

`<package>` below is the MCP's Python package, `weather_mcp` for `services/weather-mcp`.

`services/architecture-demo-mcp` is an MCP the scaffold generated, with a working example on
top, against Tiingo's market data API, with a Postgres watchlist and a Redis quote cache:
`search_assets`, `get_asset`, `get_quote`, `add_to_watchlist`, `get_watchlist` and
`remove_from_watchlist`. Every example path below is in that service. Read it next to this file when you write a feature, a
tool or a test.

## What the MCP owns and what it shares

The scaffold runs once. Every file it wrote is the MCP's own: change `mcp/server.py`, the
middleware or anything else the MCP needs. Nothing regenerates them. What every MCP shares
comes from a package it depends on instead of a copy, so a fix reaches every MCP with a version
bump:

- `packages/mcp-runtime`: the settings with their defaults, the HTTP server with its host and
  origin guard, the telemetry setup and the retrying transport of a plain HTTP upstream.
- `packages/mcp-openapi`, for an OpenAPI upstream: the client and the codegen.
- `packages/mcp-architecture`: this file, the rules below and the type check the MCP extends.

An MCP's own file calls into those packages, as `telemetry/setup.py` calls
`mcp_runtime.init_telemetry`. When one MCP needs something else, change that call or replace it
in the MCP's file. Fix something every MCP shares in one of the packages, never only in one
service. A change to `packages/mcp-scaffold` only reaches the MCPs it makes next.

## Layers

```
main.py ─▶ mcp ─▶ contexts ─▶ upstream ─┐
                          └─▶ persistence ─▶ telemetry
```

| Layer | Owns | May import |
|---|---|---|
| `main.py` | Starts telemetry, builds the server, runs it | everything |
| `mcp/` | The FastMCP server, HTTP middleware, tools and their inputs and responses | `contexts`, `upstream`, `persistence`, `telemetry` |
| `contexts/` | The domain: one folder per feature, each split into commands and queries | `upstream`, `persistence`, `telemetry` |
| `upstream/` | The system the MCP fronts: its client, settings and, for OpenAPI, the spec and generated code | `telemetry` |
| `persistence/` | Storage the MCP owns: Postgres, Redis, a key-value store | `telemetry` |
| `telemetry/` | Tracing, logging, metrics and the ops routes | nothing in the package |

`upstream` and `persistence` do not import each other. Imports only point down the table. The
package holds these and nothing else: a new top-level folder or module, such as `<package>/logic/`,
breaks the `layers` contract.

## The rules

| Rule | Enforced by |
|---|---|
| A layer only imports the layers below it. | `layers` contract |
| A layer is imported through its top level, `from <package>.upstream import X`, never `from <package>.upstream.client import X`. Inside a layer, deep imports are fine. | `protected` contracts |
| A feature is imported through its top level, `from <package>.contexts.assets import get_asset`, also by other features. Inside a feature, deep imports are fine. | `feature_privacy` contract |
| Features do not import each other in a cycle (`a → b → c → a`). | `acyclic_siblings` contract |
| A command may import queries. A query never imports a command, in its own feature or another, directly or through other modules. | `command_query_separation` contract |
| `contexts/` is flat. Each folder in it is a feature, a package named for its domain (`watchlists`), and it holds no module besides its `__init__.py`. | `feature-packages` rule |
| A feature holds only `commands/` and `queries/` folders, and those hold no folder deeper than one per command or query. | `feature-folders` rule |
| A tool folder does not nest. | `tool-folders` rule |
| Every folder with Python code has an `__init__.py`. import-linter does not see the others. | ruff `INP001` |
| A feature's `__init__.py` only re-exports: imports, `__all__` and a docstring. Define a name in a command, a query or a model module. | `feature-inits` rule |
| Every tool has a description and every parameter a `Field(description=...)`. | description check |
| A context module has at most one public function, defined before anything else in it. Its other functions and its constants are private. | `one-public-function` rule |
| A context function takes keyword arguments only: `def f(*, a, b)`. | `keyword-only` rule |
| Imports are absolute. | ruff `TID252` |
| The [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html), as far as ruff checks it, with two departures: lines run to 100 characters, and a docstring is only for what the code cannot say. One written keeps Google's format: a one-line summary, then a blank line. Besides it: no `print`, `pathlib` over `os.path`, no `else` after `return`. | `code-style` rule, ruff with `mcp-architecture`'s `code_style.toml` |
| Every type is known: no `Any`, no unannotated attribute, `@override` on an override, `super().__init__()` in a subclass. | basedpyright `all`, from `mcp-architecture`'s `type_check.json`, held by the `type-check` rule |

`mcp-architecture` is a pytest plugin. In an MCP that declares `[tool.importlinter]`, it adds
its checks to `tests/` as `tests/mcp_architecture.py`, a module that is not on disk: the
`import-contracts` rule, which runs every contract, each rule named above, the description
check and the tool surface snapshot. `uv run pytest -k mcp_architecture` runs them alone. The
MCP keeps no copy of them to loosen. An MCP that depends on `mcp-architecture` without
`[tool.importlinter]` fails to start pytest, and CI runs the checks with the MCP's `addopts`
cleared, so neither removing the table nor `-p no:mcp_architecture` skips them. The `type-check`
rule reads the configuration, not the code, so `uv run basedpyright` still has to pass on its
own.

The contracts live under `[tool.importlinter]` in `pyproject.toml`, written by the scaffold.
Never loosen a contract, add an `ignore_imports` entry or set an option such as
`exclude_type_checking_imports` to make a change pass: the `required-contracts` rule fails on
each. Move the code to the layer it belongs in. A contract of your own, stricter than these, is
fine to add after the required ones. The `required-lint` rule runs the ruff rules the
architecture relies on, `INP001`, `N999` and `TID252`, on the package itself, so neither
`[tool.ruff]` nor a `noqa` turns them off.

The code style lives in `mcp-architecture`'s `code_style.toml`. `[tool.ruff]` extends it, so
`uv run ruff check --fix` fixes most of what the `code-style` rule finds, and the rule runs it
whatever `[tool.ruff]` says. Add to `[tool.ruff]`, such as a `per-file-ignores` entry for
generated code, but never to loosen the style. A `noqa` that names its rule, with the reason
beside it, is fine, as Google's guide allows. A bare `# noqa` or `# ruff: noqa` breaks the style
(`PGH004`). What ruff cannot check is left to review: import modules rather than
names where the guide asks it, keep functions short, and avoid the guide's power features.

The type check lives in `mcp-architecture`'s `type_check.json`, which `[tool.basedpyright]`
extends. The table sets only what is the MCP's own, `extends`, `venv`, `venvPath`,
`pythonVersion` and `include = ["src", "tests"]`, and otherwise may only restate the shared
config or make a report stricter. The `type-check` rule fails on anything else there, such as
`exclude`, `ignore`, `executionEnvironments` or a report turned down, on a `pyrightconfig.json`,
which would replace the table, and on a `# pyright:` comment that changes the check of a file,
such as `# pyright: basic`. A `# pyright: ignore[rule]` on one line is fine.

## The top level is the interface

Each layer's and each feature's `__init__.py` re-exports what others may use and lists it in
`__all__`. Anything not listed there is internal. When another layer needs something internal,
decide whether it belongs in the interface, and add it to `__init__.py` if it does.

`upstream` and `persistence` expose the same names in every MCP, whatever is behind them:

| `upstream` | `persistence` | |
|---|---|---|
| `Upstream` | `Persistence` | What the contexts receive |
| `UpstreamSettings` | `PersistenceSettings` | Its settings, read from the environment |
| `open_upstream(settings)` | `open_persistence(settings)` | An async context manager the server lifespan opens. An OpenAPI upstream takes `open_upstream(http, settings)`, the client it shares with the tools served from the spec |
| `UpstreamError` | | A `ToolError`, so an upstream failure reaches the client as is |

`Upstream` is an alias of the client's own type: `OperationClient` for OpenAPI,
`httpx2.AsyncClient` for plain HTTP, the hand-written class for anything else. It keeps the type name the same in the code that
imports it, the contexts, the tools and `mcp/dependencies.py`, in every MCP. It is not an
abstraction: a context calls the client's own API, so changing the client changes them too.

## contexts

A feature is one domain concept, named in the plural of what it handles: `assets`, `quotes`,
`watchlists`. Features sit side by side. A feature never contains another feature.

Split a feature into what changes state and what reads it:

- `commands/`: places, creates, updates or deletes something upstream or in storage.
- `queries/`: reads, and changes nothing. A cache it fills changes nothing a caller sees, so
  `quotes.get_quote` is still a query though it writes to Redis.

A command may call queries, as `add_to_watchlist` calls `assets.get_asset` to check the ticker. A
query never reaches a command or anything inside `commands/`, including a command's input or
output model. A model both sides need goes in a file at the feature's top level. The contract
follows what a module takes from another feature's top level, so a query may still import
another feature's queries from there.

Start small and grow only when the code asks for it:

1. A query or command starts as one file, with its small models inline:
   `contexts/assets/queries/get_asset.py` holds `AssetDetails` and `get_asset`.
2. When its inputs or outputs grow past about ten lines, it becomes a folder with the inputs,
   the outputs and the implementation apart:

   ```
   contexts/watchlists/commands/add_to_watchlist/
   ├── __init__.py
   ├── inputs.py             AddToWatchlistInput
   ├── outputs.py            AddedToWatchlist, WatchlistRejectedError
   └── add_to_watchlist.py   add_to_watchlist()
   ```

3. Nothing nests deeper than that. A model several commands or queries share goes in a file at
   the feature's top level, such as `contexts/quotes/models.py`. It does not go in a new folder.

A module reads top down: the one public function first, then the private helpers it calls, then
its models. Python 3.14 evaluates annotations lazily, so a function may return a model defined
below it. Every function takes keyword arguments only, so a call names what it passes:

```python
async def add_to_watchlist(
    *, upstream: Upstream, persistence: Persistence, entry: AddToWatchlistInput
) -> AddedToWatchlist:
    asset = await get_asset(upstream=upstream, ticker=entry.ticker)
    stored = await add_watchlist_entry(
        persistence=persistence, watchlist=entry.watchlist, ticker=asset.ticker, ...
    )
    if isinstance(stored, WatchlistRefusal):
        raise _rejection(refusal=stored, ticker=asset.ticker, watchlist=entry.watchlist)
    ...


def _rejection(*, refusal: WatchlistRefusal, ticker: str, watchlist: str) -> WatchlistRejectedError: ...
```

Extract a private helper when it names a step, not to split a function that reads fine whole.

A context:

- Takes its dependencies as arguments, such as `upstream: Upstream`. It does not reach for
  globals or the FastMCP context.
- Returns its own pydantic models, never the upstream's. Map the vendor's field names to
  snake_case here, so a vendor change stops at this layer.
- Knows nothing about MCP. It raises its own errors (`WatchlistRejectedError`), not `ToolError`.
- May use another feature through that feature's top level: `get_watchlist` prices its
  tickers with one `quotes.get_quotes` call. If two features need each other, the shared part is a third feature.

## mcp

- `server.py`: `create_server` builds the FastMCP app. Its lifespan opens the upstream and the
  persistence, and the tools receive them through `Depends(get_upstream)` and
  `Depends(get_persistence)` from `dependencies.py`.
- `http_middleware` in `server.py` lists the MCP's own HTTP middleware, such as auth or a
  request id. `mcp_runtime.run_server` serves it after the host and origin guard and CORS, and
  `mcp_runtime.http_app` serves the same app to the tests. MCP-level middleware, which sees tool
  calls rather than HTTP requests, goes on the server in `create_server`:
  `mcp.add_middleware(...)`.
- `tools/`: `FileSystemProvider` discovers every `@tool` under it. A new tool file is picked up
  with no registration step. If one fails to import, the server refuses to start.
- A tool starts as one file, `tools/get_asset.py`. It becomes a folder when its inputs or
  responses grow past about ten lines:

  ```
  mcp/tools/add_to_watchlist/
  ├── __init__.py
  ├── add_to_watchlist.py             the @tool
  ├── add_to_watchlist_inputs.py      Annotated parameter types
  └── add_to_watchlist_responses.py   only if the tool reshapes what the context returns
  ```

- An input or response several tools share goes in `mcp/inputs/<name>.py` or
  `mcp/responses/<name>.py`, as `Ticker` does in `mcp/inputs/ticker.py`.
- A tool is thin. It turns parameters into the context's input, calls one context function,
  and turns the context's errors into `ToolError`. It holds no business rule.
- Every parameter is `Annotated[..., Field(description=...)]`. The description and the
  docstring are what the model reads, so say when to call the tool and what its ids feed into.
- Set `ToolAnnotations` honestly. A tool that orders, pays or deletes is not read-only, and one that deletes is destructive, as `remove_from_watchlist` is.
- Return the context's model unless the tool needs another shape.

## upstream

What is inside depends on what the MCP talks to. `settings.py` reads the `UPSTREAM_` env
variables either way.

- **OpenAPI.** The vendor's spec is vendored as `upstream/openapi.yml`. An operation becomes a
  tool in one of two ways:
  - **Served from the spec.** List its operationId in `EXPOSED` in `upstream/routes.py`.
    `upstream_tools` serves it with the name, arguments and output schema the spec gives
    (`getDailyPrices` becomes `get_daily_prices`), with no context and no code. It says what the spec
    says, so the description check skips it, and retries do not apply to it.
  - **A tool of our own.** List the operationId under `operation-ids` in `[tool.mcp-openapi]`
    and run `uv run mcp-openapi-codegen`. It writes `vendor_responses.py` and `operations.py`;
    never edit those two by hand. Export the operation's constant from `upstream/__init__.py`,
    then write a context that calls `upstream.call(GET_X, ...)` and a tool over it.
    `Upstream` is mcp-openapi's `OperationClient`, which validates arguments against the spec
    and parses each response into its generated model.

  A new MCP starts with its spec's first JSON operation, a GET if there is one, in both lists:
  served, and typed for when it is promoted. Serve more operations to grow the first version.
  Promote one when its output needs trimming or renaming, or a business rule, or when several
  operations make one tool: remove it from `EXPOSED` and write the tool, as
  `services/architecture-demo-mcp` did for `getDailyMeta`, now `get_asset`, and left `get_daily_prices` served.
  `upstream_http` builds the one client both kinds share, so they send the same auth.

  When the vendor changes the spec:

  1. `uv run mcp-openapi-codegen --refresh-spec` fetches it again from `spec-source` in
     `[tool.mcp-openapi]`, writes it over `upstream/openapi.yml`, lists the operationIds added
     and removed, and regenerates. Set `spec-source` first if the MCP has none.
  2. `uv run basedpyright` names each context a changed response model breaks. Fix the
     mapping there, so the change stops at `contexts/`.
  3. `uv run pytest` fails on `tests/tool_surface.generated.json` when a served tool's
     arguments or output changed. Read the diff, then accept it with
     `uv run pytest --regen-all`.

  CI runs `uv run mcp-openapi-codegen --check`, which fails when the generated code is not what
  the spec and the table generate.
- **Plain HTTP.** `Upstream` is an `httpx2.AsyncClient` with the base URL, the auth header,
  `mcp_runtime.RetryingTransport` and a hook that raises `UpstreamError` on an error status.
  Parse each response into a pydantic model in `upstream/`, so the contexts still never see raw
  JSON.
- **Anything else** (SOAP, gRPC, a vendor SDK). Write the client by hand behind the same four
  names, then open it in `server.py` and add `get_upstream` to `dependencies.py`.

## persistence

Empty when the MCP stores nothing. Otherwise an MCP owns one or more stores, and `Persistence`
holds each of them as a field, so adding a store later changes no existing caller.
`persistence/persistence.py` defines `Persistence`, `PersistenceSettings` and
`open_persistence`, which opens every store in the server lifespan.

- **Postgres.** `persistence.database` is an `async_sessionmaker`:
  `async with persistence.database() as session`. Models subclass `persistence.Base` in
  `persistence/models.py`. `uv run alembic revision --autogenerate -m "<what changed>"` writes a
  migration into `persistence/migrations/versions/` and runs ruff over it, so it keeps the code
  style. The chart's migration hook runs `alembic upgrade head` before each rollout. The base
  chart injects `DATABASE_URL`.
- **Redis.** `persistence.store` is a `py-key-value-aio` `RedisStore`, typed as the
  `AsyncKeyValue` protocol, with `get`, `put`, `delete` and a TTL per entry. `StoreSettings` is
  `mcp_runtime.RedisSettings`, set by `REDIS_URL`.

Contexts depend on what is stored, never on SQLAlchemy or Redis directly. Expose functions or
models from `persistence/__init__.py` that say what they store, as the demo's
`persistence/watchlists.py` and `persistence/quote_cache.py` do.

## telemetry

`telemetry/setup.py` passes the MCP's name to `mcp_runtime`, which sets up the rest:

- `init_telemetry(settings)` runs first in `main`, before anything logs: JSON logs in the format
  Loki expects, with trace ids, and OpenTelemetry tracing, off unless `OTEL_TRACES_EXPORTER` is
  set.
- `instrument(mcp)` mounts the `/probe`, `/health` and `/metrics` routes and returns the
  metrics middleware that `http_middleware` lists. Every tool, resource and prompt call gets a
  counter, a duration and a log line.

A metric of the MCP's own, such as upstream calls by route, is defined here with
`unique_toolkit.monitoring.MetricNamespace` and exported from `telemetry/__init__.py`.

## Settings

What every MCP configures the same way comes from `packages/mcp-runtime`, with the defaults we
always use: the server, Postgres, Redis, Zitadel, upstream retries, logging and elicitation.
Never write your own class for these. [The mcp-runtime README](../mcp-runtime/README.md) lists
each class with its env variables and defaults.

A tool that elicits reads `ElicitationSettings` before it asks. It skips the question when the
toggle for its kind (`for_disambiguation`, `for_data_modification` or `for_data_removal`) is
`disabled`, and stops waiting after `timeout_before_cancel_seconds`.

What is particular to one MCP stays in the layer that owns it, such as `UpstreamSettings` in
`upstream`, built on `shared_config` so it reads the environment the same way. `.env.example`
documents every variable. `main.py` builds the settings and passes them in, so tests pass their
own.

## deploy

- `deploy/Dockerfile` builds from the repository root, so it can copy a shared package from
  `packages/` that `[tool.uv.sources]` points at. Add a `COPY` line for every new one.
- `deploy/helm-charts/<name>/` is a thin chart over the shared `base` chart. `values.yaml` holds
  the portable defaults. The hostname, `MCP_BASE_URL` and the secrets are set per deployment in
  the Argo overlay.
- `values.schema.json` is generated: after changing `values.additional.schema.json`, run
  `scripts/render-values-schema.sh` from the repository root.
- A new env variable goes in `.env.example`, and in `values.yaml` under `env` unless it is a
  secret.
- release-please bumps the versions in `pyproject.toml`, `uv.lock`, `Chart.yaml` and the image
  tag in `values.yaml`. Never bump them by hand.

## Tests

- In the demo, `tests/conftest.py` holds `FakeTiingo`, the upstream answering through
  `httpx2.MockTransport`, and a `call_tool` fixture that calls a tool through a real FastMCP
  `Client`. Test tools this way, end to end through the context to the fake upstream.
- CI runs no Postgres or Redis. `create_server` takes the function that opens the persistence,
  so the `persistence` fixture in `tests/conftest.py` opens SQLite through `aiosqlite` and a
  `MemoryStore` in their place. That is why `Store` is typed as the `AsyncKeyValue` protocol.
  SQLite is not Postgres: a test that needs Postgres behaviour, such as a timezone or a JSON
  column, needs a real database.
- `tests/test_server.py` covers the ops routes and the host and origin guard, through the
  MCP's own `http_middleware`.
- `mcp-architecture`'s plugin adds the architecture's checks, listed under
  `tests/mcp_architecture.py`. They use the `server` fixture in `tests/conftest.py`.
- One of them compares every tool the server lists, its arguments, output, annotations and
  tags, with `tests/tool_surface.generated.json`. A change to what a client sees is a diff of
  that file in review. Accept a change you meant with `uv run pytest --regen-all`.
- Tests import through the top level too.

## Commands

```bash
# install
uv sync
# tests, contracts and folder rules
uv run pytest
# not covered by pytest
uv run ruff format . && uv run ruff check .
uv run basedpyright
# serve on http://127.0.0.1:8000/mcp, after cp .env.example .env
uv run <name>
```
