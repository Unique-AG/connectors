# MCP architecture

Every Python MCP in this repo is generated by `packages/mcp-scaffold` and keeps the shape this
file describes. It is the contract for writing code inside one, and each MCP's `AGENTS.md`
points here before it says what that MCP chose. Most of it is enforced by tools the MCP
configures, not by code of our own: ruff, basedpyright, import-linter and a few tests. A change
that breaks a rule fails one of them, and the failure names the import or the line at fault.
`bash ../../scripts/check-python-service.sh .` runs them all, in the order CI does.

`<package>` below is the MCP's Python package, `weather_mcp` for `services/weather-mcp`.
Example paths such as `contexts/prices/get_latest_close.py` come from
`services/architecture-demo-mcp`, unless the text says the demo has none.

## What the MCP owns and what it shares

The scaffold runs once. Every file it wrote is the MCP's own: change `mcp/server.py`, the
middleware or anything else the MCP needs. Nothing regenerates them. What every MCP shares
comes from a package it depends on instead of a copy, so a fix reaches every MCP with a version
bump:

- `packages/mcp-configs`: the settings with their defaults.
- `packages/mcp-openapi`, for an OpenAPI upstream: the client and the codegen.
- `packages/mcp-architecture`: this file, the code style and the type check the MCP extends, the
  import contracts the scaffold writes and the checks `tests/test_architecture.py` runs.

The rest is the MCP's own code from the start: the HTTP server with its host and origin guard
(`mcp/http.py`, `mcp/middleware.py`), the telemetry setup (`telemetry/setup.py`) and, for a
custom upstream, the client (`upstream/client.py`). When one MCP needs something else, change
its file. Fix a setting every MCP shares in `mcp-configs`, never only in one service. A change to
`packages/mcp-scaffold` only reaches the MCPs it makes next. Nothing imports `mcp-scaffold`: it
is a command-line tool, not a library.

Every file the scaffold wrote starts with a comment naming the scaffold's version and the moment
it ran, such as `# mcp-scaffold-version: 0.0.1, timestamp: 2026-10-21T09:30:00+00:00`. Leave it
on a file you edit: it tells which skeleton the file started from. A file an agent or a person
writes never gets one, not even when it is modelled on a stamped file, and a scaffold file
rewritten from scratch drops it. Neither does a file a tool writes, such as `uv.lock`, the
codegen's output, an Alembic migration or the tool surface snapshot.

## Layers

```
main.py ─▶ mcp ─▶ contexts ─▶ upstream ─┐
                          └─▶ persistence ─▶ telemetry
```

| Layer | Owns | May import |
|---|---|---|
| `main.py` | Starts telemetry, builds the server, runs it | everything |
| `mcp/` | The FastMCP server, its HTTP serving and middleware, auth, tools and their inputs and responses | `contexts`, `upstream`, `persistence`, `telemetry` |
| `contexts/` | The domain: one folder per feature | `upstream`, `persistence`, `telemetry` |
| `upstream/` | The system the MCP fronts: its client, settings and, for OpenAPI, the spec and generated code | `telemetry` |
| `persistence/` | Storage the MCP owns: Postgres, Redis, a key-value store | `telemetry` |
| `telemetry/` | Tracing, logging, metrics and the ops routes | nothing in the package |

`upstream` and `persistence` do not import each other. Imports only point down the table. The
package holds these and nothing else: a new top-level folder or module, such as `<package>/logic/`,
breaks the `layers` contract.

## The rules

| Rule | Enforced by |
|---|---|
| A layer only imports the layers below it, and the package holds no module outside them. | import-linter `layers` contract |
| A layer is imported through its top level, `from <package>.upstream import X`, never `from <package>.upstream.client import X`. Inside a layer, deep imports are fine. | import-linter `protected` contracts |
| Outside `contexts/`, code imports the domain from `<package>.contexts` only: `from <package>.contexts import get_price_performance`, never `from <package>.contexts.prices import get_price_performance`. | import-linter `protected` contract on `contexts` |
| Inside `contexts/`, a feature imports another through that feature's top level: `from <package>.contexts.prices import get_latest_close`. Inside a feature, deep imports are fine. | import-linter `feature_privacy` contract, the one contract type of our own |
| No package imports its siblings in a cycle (`a → b → c → a`), at any depth: features in `contexts/`, folders in `mcp/`, modules inside a feature. | import-linter `acyclic_siblings` contract |
| `contexts/` and `persistence/` import nothing from `fastmcp` or `mcp` themselves. | import-linter `forbidden` contract |
| Every folder with Python code has an `__init__.py`, since import-linter does not see the others. | ruff `INP001` |
| A context function takes keyword arguments only: `def f(*, a, b)`. | ruff `PLR0917`, which `[tool.ruff.lint.per-file-ignores]` turns off outside `contexts/` |
| Imports are absolute. | ruff `TID252` |
| What a past fix replaced stays replaced: a pydantic model, not a `dataclass`; `httpx2.URL` or `HttpUrl`, not `urllib.parse`; `mcp_configs.PostgresSettings`, not `ssl.create_default_context`; a Jinja2 template, not `html.escape`; `cryptography.fernet`, not `cryptography.hazmat`. | ruff `TID251` |
| The [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html), as far as ruff checks it, with three departures: lines run to 100 characters, a docstring is only for what the code cannot say, and its summary may run onto a second line. Besides it: no `print`, `pathlib` over `os.path`, no `else` after `return`, a long string split by implicit concatenation rather than `+`, and an error logged in an `except` with its traceback. | ruff, with `code_style.toml` |
| Every type is known: no `Any`, no unannotated attribute, `@override` on an override, `super().__init__()` in a subclass. A test may use a private name of the code it tests. | basedpyright `all`, with `type_check.json` |
| No file changes its own type check: a `# pyright:` comment only ignores a named rule on its line. | `scripts/check-python-service.sh` |
| Every tool has a description and every parameter a `Field(description=...)`. | `tests/test_architecture.py` |
| Every tool's input schema is a plain object, with no `anyOf`, `oneOf`, `allOf` or `not` at its root, which some clients reject. | `tests/test_architecture.py` |
| An unexpected error inside a tool reaches the client without its message: `FastMCP(mask_error_details=True)`. | `tests/test_architecture.py` |
| A settings error does not print the value it was given, which may be a secret: every settings class builds its `model_config` with `mcp_configs.shared_config`. | `tests/test_architecture.py` |
| What every tool shows a client matches `tests/tool_surface.generated.json`. | `tests/test_architecture.py` |
| `contexts/` is flat: each folder in it is a feature named for its domain, and a feature never contains another. A tool folder does not nest. A context module leads with its one public function. | review |

### Where each rule is configured

The MCP's `pyproject.toml` holds each tool's configuration, and the scaffold writes it:

- `[tool.ruff]` extends `mcp-architecture`'s `code_style.toml`, and `uv run ruff check --fix`
  fixes most of what it finds. Add to the table, such as a `per-file-ignores` entry for generated
  code, but never loosen the style. A `noqa` that names its rule, with the reason beside it, is
  fine, as Google's guide allows. A bare `# noqa` or `# ruff: noqa` breaks the style (`PGH004`).
  The `per-file-ignores` entry that limits `PLR0917` to `contexts/` sits in the MCP's table and
  not in `code_style.toml`, because ruff reads a path in an extended file from that file's folder.
- `[tool.basedpyright]` extends `type_check.json`. Make a report stricter there, never turn one
  down, and add no `pyrightconfig.json`, which would replace the table. Its
  `executionEnvironments` entry lets `tests/` use private names, for the same reason as the ruff
  entry above.
- `[tool.importlinter]` holds the contracts, which `mcp_architecture.render_importlinter` writes.
  import-linter has no way to extend a shared file, so each MCP carries its own copy. Never
  loosen a contract, add an `ignore_imports` entry or set an option such as
  `exclude_type_checking_imports` to make a change pass. Move the code to the layer it belongs
  in. A contract of your own, stricter than these, is fine to add after them.

No tool stops an MCP from loosening its own table, so review does: every change to a service's
`pyproject.toml` goes through the code owners. What ruff cannot check is left to review as well:
import modules rather than names where the guide asks it, keep functions short, and avoid the
guide's power features.

## The top level is the interface

Each layer's and each feature's `__init__.py` re-exports what others may use and lists it in
`__all__`. Anything not listed there is internal. When another layer needs something internal,
decide whether it belongs in the interface, and add it to `__init__.py` if it does.

`contexts/__init__.py` re-exports what the tools use from every feature, so `mcp/` imports
`from <package> import contexts` and calls `contexts.get_price_performance`, never naming a
feature. Its names are one flat list, so they are unique across features. A feature's own
`__init__.py` re-exports what other features may use, as `prices` does with `get_latest_close`.

`upstream` and `persistence` expose the same names in every MCP that has them, whatever is
behind them:

| `upstream` | `persistence` | |
|---|---|---|
| `Upstream` | `Persistence` | What the contexts receive |
| `UpstreamSettings` | `PersistenceSettings` | Its settings, read from the environment |
| `open_upstream(settings)` | `open_persistence(settings)` | An async context manager the server lifespan opens. An OpenAPI upstream takes `open_upstream(http, settings)`, the client it shares with the tools served from the spec |
| `UpstreamError` | | A `ToolError`, so an upstream failure reaches the client as is |

`Upstream` is the client's own type: an alias of `OperationClient` for OpenAPI, and the class in
`upstream/client.py` for a custom upstream. It keeps the type name the same in the code that
imports it, the contexts, the tools and `mcp/dependencies.py`, in every MCP. It is not an
abstraction: a context calls the client's own API, so changing the client changes them too.
Nothing outside `upstream/` imports `upstream/client.py` or any other module in it: the
`protected` contract fails on `from <package>.upstream.client import Upstream`.

## contexts

A feature is one domain concept, named in the plural of what it handles: `prices`,
`portfolios`. Features sit side by side. A feature never contains another feature, and organizes
its own modules as its code asks.

Start small and grow only when the code asks for it:

1. A function starts as one module, with its small models inline:
   `contexts/prices/get_price_performance.py` holds `get_price_performance`, `PricePerformance`
   and `PerformanceUnavailableError`.
2. When its inputs or outputs grow past about ten lines, it becomes a folder with the inputs,
   the outputs and the implementation apart. No feature in the demo has grown this far. If
   `record_position` did:

   ```
   contexts/portfolios/record_position/
   ├── __init__.py
   ├── inputs.py             PositionInput
   ├── outputs.py            PositionRejectedError
   └── record_position.py    record_position()
   ```

3. A model several modules of a feature share goes in a file at the feature's top level, such as
   `contexts/portfolios/models.py`, whose `PortfolioValuation` both `record_position` and
   `value_portfolio` return.

A module reads top down: the one public function first, then the private helpers it calls, then
its models. Python 3.14 evaluates annotations lazily, so a function may return a model defined
below it. Every function takes keyword arguments only, so a call names what it passes:

```python
async def get_price_performance(
    *,
    upstream: Upstream,
    persistence: Persistence,
    ticker: str,
    start_date: date,
    end_date: date | None,
) -> PricePerformance:
    closes = await get_daily_closes(
        upstream=upstream,
        persistence=persistence,
        ticker=ticker,
        start_date=start_date,
        end_date=end_date,
    )
    if len(closes) < _MIN_TRADING_DAYS:
        raise PerformanceUnavailableError(...)
    daily_returns = [later.close / earlier.close - 1 for earlier, later in pairwise(closes)]
    return PricePerformance(
        ...,
        annualized_volatility=_annualized_volatility(daily_returns=daily_returns),
        max_drawdown=_max_drawdown(closes=closes),
    )


def _annualized_volatility(*, daily_returns: list[float]) -> float | None: ...


def _max_drawdown(*, closes: list[DailyClose]) -> float: ...


class PricePerformance(BaseModel): ...


class PerformanceUnavailableError(Exception): ...
```

Extract a private helper when it names a step, not to split a function that reads fine whole.

A context:

- Takes its dependencies as arguments, such as `upstream: Upstream` and
  `persistence: Persistence`. It does not reach for globals or the FastMCP context.
- May read and write the MCP's own storage through `persistence`'s top level:
  `record_position` stores a holding with `save_position`, and `value_portfolio` reads them
  back with `list_positions`. It calls what `persistence` exposes, never SQLAlchemy or Redis
  directly (see [persistence](#persistence)).
- Returns its own pydantic models, never the upstream's. Map the vendor's field names to
  snake_case here, so a vendor change stops at this layer.
- Knows nothing about MCP. It raises its own errors (`PositionRejectedError`), not `ToolError`.
- May use another feature through that feature's top level: `value_portfolio` prices each
  position with `get_latest_close`, imported from `<package>.contexts.prices`. If two features
  need each other, the shared part is a third feature.

## mcp

- `server.py`: `create_server` builds the FastMCP app. Its lifespan opens the upstream and the
  persistence, and the tools receive them through `Depends(get_upstream)` and
  `Depends(get_persistence)` from `dependencies.py`.
- `http.py`: `run_server` serves the app over streamable HTTP at `/mcp`, stateless, and
  `http_app` serves the same app to the tests. `run_server` refuses to bind beyond loopback
  while the server has no auth provider, `FastMCP(auth=...)`, so an MCP without auth runs
  locally but never in a pod.
- `middleware.py`: `http_middleware` puts the host and origin guard first, then CORS, then the
  MCP's own HTTP middleware, such as a request id, after `instrument(mcp)`. The guard lets a
  request through only for a host of `MCP_BASE_URL` (or `localhost`) and, from a browser, an
  allowed origin. `/probe`, `/health` and `/metrics` skip it, since Kubernetes and Prometheus
  reach the pod by IP. MCP-level middleware, which sees tool calls rather than HTTP requests,
  goes on the server in `create_server`: `mcp.add_middleware(...)`.
- `auth/`, once the MCP has auth: what FastMCP does not provide itself, behind its own
  `__init__.py` (see [Auth](#auth)).
- `tools/`: `FileSystemProvider` discovers every `@tool` under it. A new tool file is picked up
  with no registration step. If one fails to import, the server refuses to start.
- A tool starts as one file, `tools/get_price_performance.py`. It becomes a folder when its
  inputs or responses grow past about ten lines:

  ```
  mcp/tools/record_position/
  ├── __init__.py
  ├── record_position.py             the @tool
  ├── record_position_inputs.py      Annotated parameter types
  └── record_position_responses.py   only if the tool reshapes what the context returns
  ```

  The demo's `record_position` has no responses file, since it returns the context's
  `PortfolioValuation` as it is.

- An input or response several tools share goes in `mcp/inputs/<name>.py` or
  `mcp/responses/<name>.py`, as `Ticker` does in `mcp/inputs/ticker.py`.
- A tool is thin. It turns parameters into the context's input, calls one context function,
  and turns the context's errors into `ToolError`. It holds no business rule.
- Every parameter is `Annotated[..., Field(description=...)]`. The description and the
  docstring are what the model reads, so say when to call the tool and what its ids feed into.
- Set `ToolAnnotations` honestly. A tool that orders, pays or deletes is not read-only, and one
  that deletes is destructive. `record_position` writes, so it is not read-only, and replacing a
  holding destroys nothing, so it is not destructive. The demo has no tool that deletes.
- Return the context's model unless the tool needs another shape.

## upstream

Empty when the MCP calls no system of its own: an `__init__.py` with an empty `__all__`, so the
layers contract still sees the layer. Otherwise what is inside depends on what the MCP talks to,
and `settings.py` reads the `UPSTREAM_` env variables either way. Adding an upstream later
means writing the client here, opening it in `server.py` and adding `get_upstream` to
`dependencies.py`.

- **OpenAPI.** The vendor's spec is vendored as `upstream/openapi.yml`. An operation becomes a
  tool in one of two ways:
  - **Served from the spec.** List its operationId in `EXPOSED` in `upstream/routes.py`.
    `upstream_tools` serves it with the name, arguments and output schema the spec gives
    (`getDailyPrices` becomes `get_daily_prices`), with no context and no code. It says what the spec
    says, so the description check skips it, and retries do not apply to it.
  - **A tool of our own.** List the operationId under `operation-ids` in `[tool.mcp-openapi]`
    and run `uv run mcp-openapi-codegen`. It writes `vendor_responses.py` and `operations.py`
    in `upstream/generated/`; never edit that package by hand. Export the operation's constant from `upstream/__init__.py`,
    then write a context that calls `upstream.call(GET_X, ...)` and a tool over it.
    `Upstream` is mcp-openapi's `OperationClient`, which validates arguments against the spec
    and parses each response into its generated model.

  A new MCP starts with its spec's first JSON operation, a GET if there is one, in both lists:
  served, and typed for when it is promoted. Serve more operations to grow the first version.
  Promote one when its output needs trimming or renaming, or a business rule, or when several
  operations make one tool: remove it from `EXPOSED` and write the tool. An operation may also
  stay served while a tool of our own builds on it: the demo serves `get_daily_prices` for the
  raw bars, and `get_price_performance` turns the same `getDailyPrices` into a summary.
  `upstream_http` builds the one client both kinds share, so they send the same auth.

  When the vendor changes the spec:

  1. `uv run mcp-openapi-codegen --refresh-spec` fetches it again from `spec-source` in
     `[tool.mcp-openapi]`, writes it over `upstream/openapi.yml`, lists the operationIds added
     and removed, and regenerates. Set `spec-source` first if the MCP has none.
  2. `uv run basedpyright` names each context a changed response model breaks. Fix the
     mapping there, so the change stops at `contexts/`.
  3. `uv run pytest` fails on `tests/tool_surface.generated.json` when a served tool's
     arguments or output changed. Read the diff, then accept it with
     `uv run pytest --regen-all`.

  CI runs `uv run mcp-openapi-codegen --check`, which fails when the generated code is not what
  the spec and the table generate.
- **Custom.** `upstream/client.py` starts as a small HTTP client, ours to change: `Upstream` has
  one `request(method, path, adapter, params=..., json=...)` for any method and path. It
  validates every body with the `TypeAdapter` it is given, so a context only ever receives a
  pydantic model, and raises `UpstreamError` on an error status, a transport error or a body
  that does not fit. As in mcp-openapi, the error names the status, method and URL without its
  query, and the start of an error body goes to the server log only. It retries with `RetrySettings` as mcp-openapi's `RetryAfterPolicy` does,
  written out rather than imported: a status in `statuses` after its `Retry-After` or a backoff,
  within `max_wait_seconds`, any request on a 429 and only an idempotent one on another status.
  Put the response models in `upstream/` and export them from `upstream/__init__.py`. For
  another protocol (SOAP, gRPC, a vendor SDK), replace the client behind the same four names.
  When the upstream limits concurrent requests, hold a lock around each attempt and release it
  while a retry waits, as mcp-openapi's `LockConfig` does.

## persistence

Empty when the MCP stores nothing. Otherwise an MCP owns one or more stores, and `Persistence`
holds each of them as a field, so adding a store later changes no existing caller.
`persistence/persistence.py` defines `Persistence`, `PersistenceSettings` and
`open_persistence`, which opens every store in the server lifespan.

- **Postgres.** `persistence.database` is an `async_sessionmaker`:
  `async with persistence.database() as session`. Models subclass `persistence.Base` in
  `persistence/models.py`. `uv run alembic revision --autogenerate -m "<what changed>"` writes a
  migration into `persistence/migrations/versions/` and runs ruff over it, so it keeps the code
  style. The chart's migration hook runs `alembic upgrade head` before each rollout. The base
  chart injects `DATABASE_URL`.
- **Redis.** `persistence.store` is a `py-key-value-aio` `RedisStore`, typed as the
  `AsyncKeyValue` protocol, with `get`, `put`, `delete` and a TTL per entry. `StoreSettings` is
  `mcp_configs.RedisSettings`, set by `REDIS_URL`.

Contexts depend on what is stored, never on SQLAlchemy or Redis directly. Expose functions or
models from `persistence/__init__.py` that say what they store, such as
`persistence/positions.py` and `persistence/price_cache.py`.

## telemetry

`telemetry/setup.py` sets it up under the MCP's name, with `unique_mcp` and `unique_toolkit`:

- `init_telemetry(settings)` runs first in `main`, before anything logs: JSON logs in the format
  Loki expects, with trace ids, and OpenTelemetry tracing, off unless `OTEL_TRACES_EXPORTER` is
  set.
- `instrument(mcp)` mounts the `/probe`, `/health` and `/metrics` routes and returns the
  metrics middleware that `http_middleware` lists. Every tool, resource and prompt call gets a
  counter, a duration and a log line.

A metric of the MCP's own, such as upstream calls by route, is defined here with
`unique_toolkit.monitoring.MetricNamespace` and exported from `telemetry/__init__.py`.

## Settings

What every MCP configures the same way comes from `packages/mcp-configs`, with the defaults we
always use: the server, Postgres, Redis, Zitadel, upstream retries, logging and elicitation.
Never write your own class for these. [The mcp-configs README](../mcp-configs/README.md) lists
each class with its env variables and defaults.

A tool that elicits reads `ElicitationSettings` before it asks. It skips the question when the
toggle for its kind (`for_disambiguation`, `for_data_modification` or `for_data_removal`) is
`disabled`, and stops waiting after `timeout_before_cancel_seconds`.

What is particular to one MCP stays in the layer that owns it, such as `UpstreamSettings` in
`upstream`, built on `shared_config` so it reads the environment the same way. `.env.example`
documents every variable. `main.py` builds the settings and passes them in, so tests pass their
own.

## Auth

An MCP starts without auth, and `run_server` keeps it on loopback until it has an auth provider.
Adding one:

1. Use what FastMCP provides first: `fastmcp.server.auth` has token verifiers (`JWTVerifier`,
   `StaticTokenVerifier`, introspection), `OAuthProxy`, `OIDCProxy` and, under
   `fastmcp.server.auth.providers`, providers for common identity services. A Zitadel sign-in is
   `unique_mcp.auth.zitadel.create_zitadel_oidc_proxy`, configured by the same environment as
   `ZitadelSettings` from `mcp-configs`. Write code only for what neither provides.
2. Code of our own lives in `mcp/auth/`, exported from its `__init__.py`. `create_server` passes
   the provider to `FastMCP(auth=...)`.
3. The upstream never sees how the user signed in. When it needs the caller's credentials,
   `get_upstream` in `mcp/dependencies.py` reads them, such as with
   `fastmcp.server.dependencies.get_access_token()`, and hands the client either the values
   themselves or a function that returns them, through its constructor. Contexts and
   `upstream/` import nothing from auth, and no token reaches a context.

## deploy

- `deploy/Dockerfile` builds from the repository root, so it can copy a shared package from
  `packages/` that `[tool.uv.sources]` points at. Add a `COPY` line for every new one.
- `deploy/helm-charts/<name>/` is a thin chart over the shared `base` chart. `values.yaml` holds
  the portable defaults. The hostname, `MCP_BASE_URL` and the secrets are set per deployment in
  the Argo overlay.
- `values.schema.json` is generated: after changing `values.additional.schema.json`, run
  `scripts/render-values-schema.sh` from the repository root.
- A new env variable goes in `.env.example`, and in `values.yaml` under `env` unless it is a
  secret.
- release-please bumps the versions in `pyproject.toml`, `uv.lock`, `Chart.yaml` and the image
  tag in `values.yaml`. Never bump them by hand.

## Tests

- Answer the upstream from `tests/conftest.py` through `httpx2.MockTransport`, and call each
  tool with a `call_tool` fixture that uses a real FastMCP `Client`. Test tools this way, end
  to end through the context to the fake upstream.
- CI runs no Postgres or Redis. `create_server` takes the function that opens the persistence,
  so the `persistence` fixture in `tests/conftest.py` opens SQLite through `aiosqlite` and a
  `MemoryStore` in their place. That is why `Store` is typed as the `AsyncKeyValue` protocol.
  SQLite is not Postgres: a test that needs Postgres behaviour, such as a timezone or a JSON
  column, needs a real database.
- `tests/test_server.py` covers the ops routes, the host and origin guard, CORS and the refusal
  to serve beyond loopback without auth, through the MCP's own `http_app` and `run_server`.
- A custom upstream's `tests/test_upstream.py` covers its client: the parse into the model, the
  auth header and each retry rule, against `httpx2.MockTransport`.
- `tests/test_architecture.py` runs `mcp-architecture`'s checks of what a client sees, against
  the `server` fixture in `tests/conftest.py`: the descriptions, the input schemas, the masked
  errors and the settings that keep their input out of an error.
- One of them compares every tool the server lists, its arguments, output, annotations and
  tags, with `tests/tool_surface.generated.json`. A change to what a client sees is a diff of
  that file in review. Accept a change you meant with `uv run pytest --regen-all`.
- Tests import through the top level too.

## Commands

```bash
# install
uv sync
# every check CI runs, in its order
bash ../../scripts/check-python-service.sh .
# or one at a time
uv run ruff format . && uv run ruff check .
uv run basedpyright
uv run lint-imports
uv run pytest
# serve on http://127.0.0.1:8000/mcp, after cp .env.example .env
uv run <name>
```
